# Decisions: Documentation Standards

> Stack: documentation | Status: ACTIVE | Applicable: YES
>
> Created 2026-03-16. Best-practice decisions for Architecture Decision Records,
> API documentation, code documentation, onboarding, and documentation
> governance for full-stack applications.

---

## Decided Items

| ID      | Priority | Scope                                 | Decision                                                                                                                                                                                                                                                                                                                                                                                            | Notes | Date       |
| ------- | -------- | ------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----- | ---------- |
| DEC-445 | HIGH     | All Phases (ADR Process)              | Record all significant architectural decisions as ADRs using a lightweight template: Title, Status (proposed/accepted/deprecated/superseded), Context, Decision, Consequences. Store ADRs in the repository (`docs/adr/`). ADRs are immutable once accepted — new decisions supersede old ones. Every PR with architectural impact must reference or create an ADR.                                 |       | 2026-03-16 |
| DEC-446 | HIGH     | Phase 2 (API Documentation)           | All REST APIs must have auto-generated documentation from the OpenAPI spec (see DEC-315). Host interactive API docs (Swagger UI, Redocly, or Stoplight) accessible to all developers. Document authentication requirements, error responses, and example payloads for every endpoint. API docs must be updated atomically with code changes — stale docs are a build failure.                       |       | 2026-03-16 |
| DEC-447 | HIGH     | All Phases (README Standard)          | Every deployable service and library package must have a README with: purpose (1-paragraph), quickstart (copy-pasteable setup), configuration (all env vars/flags), architecture (high-level diagram), dependencies (external services), and contribution guide link. README is the first thing a new developer reads — optimize for onboarding speed.                                              |       | 2026-03-16 |
| DEC-448 | MEDIUM   | Phase 2 (Code Documentation)          | Document the "why", not the "what" — code should be self-documenting for the "what". Add JSDoc/TSDoc for all public API functions, classes, and types in shared libraries. No documentation for private/internal implementation unless the logic is non-obvious. Avoid stale comments — delete comments that restate the code. Prefer typed parameters over lengthy parameter description comments. |       | 2026-03-16 |
| DEC-449 | MEDIUM   | Phase 2 (Runbook / Operations Docs)   | Every production service must have a runbook (see DEC-423 for content requirements). Document: deployment procedure, rollback procedure, common failure modes and remediations, monitoring dashboard links, escalation contacts. Operations docs are part of the release checklist — no deployment without updated runbook.                                                                         |       | 2026-03-16 |
| DEC-450 | MEDIUM   | Phase 2 (Architecture Diagrams)       | Maintain a system architecture diagram (C4 Level 1: Context, Level 2: Container, Level 3: Component for complex services). Use diagram-as-code (Mermaid, PlantUML, Structurizr) — no static image files that can't be diff'd. Store diagrams in the repository. Update diagrams when services, dependencies, or data flows change.                                                                  |       | 2026-03-16 |
| DEC-451 | MEDIUM   | All Phases (Onboarding Documentation) | Maintain an onboarding guide covering: environment setup (< 30 minutes from clone to running), repository structure, key architectural patterns, testing approach, deployment workflow, and team conventions. Test the onboarding guide with every new team member and update based on their friction points.                                                                                       |       | 2026-03-16 |
| DEC-452 | LOW      | All Phases (Documentation Governance) | Assign documentation ownership per service/area. Conduct quarterly documentation reviews to identify and remove stale content. Mark documentation with last-reviewed date. Broken links are treated as bugs. Documentation PRs follow the same review process as code PRs. Use a docs-as-code approach — documentation lives in the repository, not in wikis or Confluence.                         |       | 2026-03-16 |
