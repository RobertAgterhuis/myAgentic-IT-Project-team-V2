# Decisions: Internationalization & Localization

> Stack: i18n | Status: ACTIVE | Applicable: YES
>
> Created 2026-03-16. Best-practice decisions for internationalization
> framework, locale management, translation workflow, and localization
> governance for full-stack applications.

---

## Decided Items

| ID      | Priority | Scope                                     | Decision                                                       | Notes                                                                                                                                                                                                                                                                                                                                       | Date       |
| ------- | -------- | ----------------------------------------- | -------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------- |
| DEC-399 | HIGH     | Phase 3 (i18n Framework)                  | What i18n framework is mandatory?                              | Use a proven i18n library: `react-intl` (FormatJS), `i18next` + `react-i18next`, or equivalent. All user-facing strings must go through the i18n system — no hardcoded strings in components. Server-side messages (API errors, emails) must also be localized. Select one framework and use it consistently across the entire application. | 2026-03-16 |
| DEC-400 | HIGH     | Phase 3 (Locale Detection)                | How must user locale be detected and applied?                  | Detection priority: (1) user preference (stored in profile), (2) `Accept-Language` header, (3) browser `navigator.language`, (4) application default. Allow users to override locale at any time. Persist locale preference. Apply locale to: text, dates, numbers, currency, sorting.                                                      | 2026-03-16 |
| DEC-401 | HIGH     | Phase 3 (String Extraction)               | How must translatable strings be managed in source code?       | Use message IDs for all translatable strings. IDs must be descriptive (`login.button.submit`, not `btn1`). Provide default English text alongside IDs. Run automated string extraction in CI to detect untranslated strings. No string concatenation for translatable phrases — use ICU MessageFormat for interpolation.                    | 2026-03-16 |
| DEC-402 | MEDIUM   | Phase 3 (Translation Workflow)            | What translation management workflow is required?              | Use a translation management system (TMS) such as Weblate, Crowdin, or Lokalise. Source strings are exported from the codebase, translated in the TMS, and imported back automatically (CI integration). Translation review by native speakers is required before merge. Support translation memory for consistency.                        | 2026-03-16 |
| DEC-403 | MEDIUM   | Phase 3 (Date/Number/Currency Formatting) | What formatting rules apply to dates, numbers, and currencies? | Use `Intl` APIs (Intl.DateTimeFormat, Intl.NumberFormat, Intl.RelativeTimeFormat) for locale-aware formatting. Never format dates with string concatenation. Store dates as UTC/ISO 8601 — convert to local timezone only for display. Currency follows the user's locale or the transaction's currency — never assumed.                    | 2026-03-16 |
| DEC-404 | MEDIUM   | Phase 3 (RTL Support)                     | What Right-to-Left (RTL) language support is required?         | Application layout must support RTL when RTL locales (Arabic, Hebrew, Farsi) are in scope. Use CSS logical properties (`margin-inline-start` instead of `margin-left`). Test UI in RTL mode as part of the localization QA process. Use `dir="auto"` for user-generated content.                                                            | 2026-03-16 |
| DEC-405 | MEDIUM   | Phase 3 (Pluralization & Gender)          | What pluralization and gender rules apply?                     | Use ICU MessageFormat for pluralization (handles language-specific plural rules: zero, one, two, few, many, other). Support gender-neutral translations where possible. Avoid grammatical assumptions based on English rules. Test with languages that have complex plural forms (e.g., Polish, Arabic).                                    | 2026-03-16 |
| DEC-406 | LOW      | Phase 3 (Locale Testing)                  | What localization testing is required?                         | Test pseudo-localization (expanded characters, mirrored text) to catch layout issues early. Visual regression tests must include at least one non-Latin locale. Test longest translations against UI constraints (German/Finnish strings are typically 30–40% longer than English). Validate date/number formatting in integration tests.   | 2026-03-16 |
