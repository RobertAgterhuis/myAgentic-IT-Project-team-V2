# Decisions: Background Jobs & Message Queues

> Stack: background-jobs | Status: ACTIVE | Applicable: YES
>
> Created 2026-03-16. Best-practice decisions for asynchronous processing, job
> scheduling, message queue governance, worker patterns, and dead-letter handling
> for full-stack applications.

## Decided Items

| DEC-463 | HIGH     | Phase 2 (Async Processing Strategy)   | When must work be processed asynchronously?                    | Move work to background when: (a) it takes > 2 seconds, (b) it doesn't need an immediate user response, (c) it involves external service calls that may fail, (d) it's scheduled/recurring. Never block HTTP request threads with long-running operations. Return 202 Accepted with a status polling URL or use WebSockets for completion notification.                               | 2026-03-16 |
| DEC-464 | HIGH     | Phase 2 (Message Queue Selection)     | What message queue/broker strategy is mandatory?               | Select queue technology based on needs: Redis (BullMQ) for simple job queues in Node.js, RabbitMQ for complex routing and guaranteed delivery, Azure Service Bus / AWS SQS for cloud-native managed queues, Kafka for event streaming and high-throughput scenarios. Justify technology choice in an ADR. Use at most 2 queue technologies per system.                                | 2026-03-16 |
| DEC-465 | HIGH     | Phase 2 (Idempotent Processing)       | What idempotency guarantees must job/message handlers provide? | All message consumers and job handlers must be idempotent — processing the same message twice must produce the same result. Use deduplication keys or idempotency tokens. Design for at-least-once delivery (the default for most queues). Log duplicate detections at INFO level. Never assume exactly-once delivery unless the platform explicitly guarantees it.                   | 2026-03-16 |
| DEC-466 | HIGH     | Phase 2 (Dead Letter Queues)          | What dead-letter handling is mandatory?                        | All queues must have a configured dead-letter queue (DLQ). Messages move to DLQ after max retry attempts (default: 3). DLQ messages must be monitored and alerted on. Provide tooling to inspect, replay, or purge DLQ messages. DLQ messages retain the original message body, headers, and failure reason. Never auto-delete DLQ messages without review.                           | 2026-03-16 |
| DEC-467 | MEDIUM   | Phase 2 (Job Scheduling)              | What scheduled/recurring job patterns are mandatory?           | Use a job scheduler (node-cron, BullMQ repeatable jobs, or cloud-native scheduler) for recurring tasks. All scheduled jobs must be: idempotent, observable (logged start/end/duration), and have timeout limits. Use distributed locks (Redis, database) to prevent duplicate execution in multi-instance deployments. Document all scheduled jobs with purpose, schedule, and owner. | 2026-03-16 |
| DEC-468 | MEDIUM   | Phase 2 (Backpressure & Rate Control) | What backpressure and rate control mechanisms are required?    | Configure concurrency limits on all queue consumers (e.g., max 10 concurrent jobs). Implement rate limiting for jobs that call external APIs. Use queue-level backpressure (pause consumption when downstream is overloaded). Monitor queue depth — alert when depth exceeds normal baseline by 3x. Never allow unbounded queue growth.                                               | 2026-03-16 |
| DEC-469 | MEDIUM   | Phase 2 (Job Observability)           | What observability is required for background jobs?            | Log job lifecycle: enqueued, started, completed, failed, retried. Include job ID, type, duration, and attempt number. Expose metrics: jobs processed/sec, failure rate, average duration, queue depth. Trace jobs with the same traceId as the originating request. Dashboard for job health with alerting on failure rate > 5%.                                                      | 2026-03-16 |
| DEC-470 | MEDIUM   | Phase 2 (Message Schema & Versioning) | What message schema governance is required?                    | All messages must have a defined schema (JSON Schema, Avro, or TypeScript type). Include a `version` field in every message envelope. Consumers must handle unknown fields gracefully (forward compatibility). Breaking schema changes require a new message type or version — old consumers must not break. Document message schemas alongside the producing service.                | 2026-03-16 |
| DEC-471 | LOW      | Phase 2 (Priority Queues)             | When should job priority be implemented?                       | Use priority queues when different job types have different latency requirements (e.g., user-triggered actions priority over batch processing). Define at most 3 priority levels (high, normal, low). Ensure low-priority jobs are not starved — set minimum throughput guarantees. Document priority assignment criteria. Default priority is "normal".                              | 2026-03-16 |
| DEC-472 | LOW      | Phase 2 (Graceful Shutdown)           | What graceful shutdown behavior is required for workers?       | Workers must handle SIGTERM gracefully: stop accepting new jobs, complete in-progress jobs (within a timeout), and then exit. Timeout for in-progress job completion: 30 seconds (configurable). Jobs interrupted by forced shutdown must be returned to the queue automatically. Log shutdown lifecycle events. Test graceful shutdown behavior in integration tests.                | 2026-03-16 |
