# Decisions: Security

> Stack: security | Status: ACTIVE | Applicable: YES
>
> Created 2026-03-16. Best-practice decisions for application security, OWASP
> compliance, headers, input validation, dependency security, and security
> testing for full-stack applications.

| DEC-367 | HIGH     | Phase 2 (OWASP Baseline)                 | What application security baseline is mandatory?                        | All applications must be evaluated against the OWASP Top 10 (latest version). Address all HIGH and CRITICAL findings before production release. Track MEDIUM findings as tech debt with a remediation timeline. Include OWASP checks in the Definition of Done.                                                                                                                          | 2026-03-16 |
| DEC-368 | HIGH     | Phase 2 (Input Validation)               | What input validation strategy is mandatory?                            | Validate all input at the system boundary (API layer). Use allowlist validation — define what is valid, reject everything else. Validate data type, length, range, and format. Sanitize all user input before rendering (HTML encoding for XSS prevention). Never trust data from the client, middleware, or external services.                                                          | 2026-03-16 |
| DEC-369 | HIGH     | Phase 2 (Security Headers)               | What HTTP security headers must all responses include?                  | Mandatory headers: `Strict-Transport-Security` (HSTS, min 1 year, includeSubDomains), `Content-Security-Policy` (restrictive, no `unsafe-inline`/`unsafe-eval` in production), `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY` (or CSP frame-ancestors), `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy` (restrict camera, microphone, geolocation). | 2026-03-16 |
| DEC-370 | HIGH     | Phase 2 (CORS Policy)                    | What CORS policy is mandatory?                                          | Never use `Access-Control-Allow-Origin: *` for authenticated APIs. Allowlist specific origins explicitly. Restrict `Access-Control-Allow-Methods` to methods actually used. Set `Access-Control-Max-Age` for preflight caching. Credentials mode requires explicit origin (not wildcard). Review CORS config quarterly.                                                                  | 2026-03-16 |
| DEC-371 | HIGH     | Phase 2 (HTTPS / TLS)                    | What transport security rules apply?                                    | HTTPS is mandatory for all environments including development. TLS 1.2 is the minimum version; TLS 1.3 preferred. Redirect all HTTP traffic to HTTPS. Use HSTS to prevent downgrade attacks. Certificates must be auto-renewed (Let's Encrypt, Azure, or equivalent).                                                                                                                    | 2026-03-16 |
| DEC-372 | HIGH     | Phase 2 (Dependency Scanning)            | What dependency vulnerability scanning is mandatory?                    | Run automated dependency vulnerability scanning (npm audit, Dependabot, Snyk, or Trivy) on every CI build. Fail the build for HIGH/CRITICAL vulnerabilities with known exploits. Review and update dependencies at least monthly. Maintain a software bill of materials (SBOM) for production deployments.                                                                               | 2026-03-16 |
| DEC-373 | HIGH     | Phase 2 (Secret Management)              | How must secrets and credentials be managed?                            | Never commit secrets to source code. Use a secret manager (Azure Key Vault, AWS Secrets Manager, HashiCorp Vault). Inject secrets via environment variables or secret references — not config files. Rotate secrets on a defined schedule (90 days max for API keys). Scan all commits for secret leaks (gitleaks, GitHub secret scanning).                                              | 2026-03-16 |
| DEC-374 | HIGH     | Phase 2 (CSRF Protection)                | What CSRF protection strategy is mandatory?                             | Use SameSite cookies (`Strict` or `Lax`) as primary CSRF defense. Implement anti-CSRF tokens (synchronizer token pattern) for state-changing operations when SameSite is insufficient. APIs using only Bearer tokens in Authorization headers are exempt (not cookie-based). Verify `Origin` header on form submissions.                                                                 | 2026-03-16 |
| DEC-375 | MEDIUM   | Phase 2 (Rate Limiting & DoS Protection) | What rate limiting and denial-of-service mitigation is required?        | Implement rate limiting at the API gateway or application layer. Define rate tiers: public endpoints (stricter), authenticated (moderate), internal (relaxed). Use sliding window counters. Return `429` + `Retry-After`. Deploy WAF rules for common attack patterns (SQLi, XSS, path traversal). Set request body size limits.                                                         | 2026-03-16 |
| DEC-376 | MEDIUM   | Phase 2 (SQL Injection Prevention)       | What SQL injection prevention is required beyond parameterized queries? | Use parameterized queries or ORM-generated queries exclusively (see DEC-324). Additionally: apply principle of least privilege for database accounts (no admin access from application). Escape dynamic identifiers (table/column names) when unavoidable. Run SAST tools that detect SQL injection patterns.                                                                            | 2026-03-16 |
| DEC-377 | MEDIUM   | Phase 2 (Security Testing)               | What security testing is mandatory in the SDLC?                         | Run SAST (Static Application Security Testing) in CI on every PR. Run DAST (Dynamic Application Security Testing) against staging before each release. Conduct penetration testing at least annually and after major architecture changes. Track all findings in a vulnerability register with SLA-based remediation timelines.                                                          | 2026-03-16 |
| DEC-378 | MEDIUM   | Phase 2 (Secure Development Practices)   | What secure development practices are mandatory?                        | Security training for all developers (at least annual OWASP awareness). Security review required for PRs touching auth, payment, PII, or crypto. Use pre-commit hooks for secret scanning. Pin dependencies to exact versions or lockfiles. Review third-party packages before adoption (maintenance, license, CVE history).                                                             | 2026-03-16 |
