# Decisions: Git Workflow & Release Management

> Stack: git-workflow | Status: ACTIVE | Applicable: YES
>
> Created 2026-03-16. Best-practice decisions for branching strategy, commit
> conventions, PR process, versioning, and release management for full-stack
> applications.

---

## Decided Items

| ID      | Priority | Scope                          | Decision                                                                                                                                                                                                                                                                                                                                                      | Notes | Date       |
| ------- | -------- | ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----- | ---------- |
| DEC-389 | HIGH     | Phase 2 (Branching Strategy)   | Use trunk-based development with short-lived feature branches. `main` is always deployable. Feature branches must be merged within 2 business days (prefer same-day). Long-lived branches are prohibited. Use feature flags for incomplete features — not branches. Release branches acceptable for hotfix isolation if needed.                               |       | 2026-03-16 |
| DEC-390 | HIGH     | Phase 2 (Commit Conventions)   | Use Conventional Commits format: `type(scope): description`. Required types: `feat`, `fix`, `docs`, `style`, `refactor`, `test`, `chore`, `ci`, `perf`. Enforce via commitlint in a pre-commit hook. Commit messages must reference the issue/ticket number. Breaking changes must use `BREAKING CHANGE:` footer.                                             |       | 2026-03-16 |
| DEC-391 | HIGH     | Phase 2 (Pull Request Process) | Every change to `main` must go through a PR. PR must pass all CI checks (build, lint, test, security scan) before review. Minimum 1 approving review required (2 for security-sensitive or architectural changes). PR description must include: what, why, how to test, and link to issue. Self-merging after approval is permitted for non-security changes. |       | 2026-03-16 |
| DEC-392 | HIGH     | Phase 2 (Semantic Versioning)  | Use Semantic Versioning (SemVer 2.0): `MAJOR.MINOR.PATCH`. Automate version bumps from Conventional Commits (e.g., `feat` → minor, `fix` → patch, `BREAKING CHANGE` → major). Tag every release in Git. Publish release notes automatically from commit history.                                                                                              |       | 2026-03-16 |
| DEC-393 | HIGH     | Phase 2 (Protected Branches)   | `main` branch: require PR, require CI pass, require review approval, prohibit force-push, prohibit deletion. No direct commits to `main` — even for administrators. Require signed commits (GPG or SSH) for all contributors. Branch protection rules are managed as code in the repository.                                                                  |       | 2026-03-16 |
| DEC-394 | MEDIUM   | Phase 2 (Merge Strategy)       | Use squash-and-merge as the default for feature branches (clean history). Use merge commits for release/hotfix branches (preserve history). Rebase-and-merge acceptable for single-commit PRs. Delete source branch after merge. Linear history on `main` is preferred.                                                                                       |       | 2026-03-16 |
| DEC-395 | MEDIUM   | Phase 2 (Changelog)            | Auto-generate `CHANGELOG.md` from Conventional Commits on every release. Changelog must include: version number, date, grouped changes (features, fixes, breaking changes). Keep a human-readable format. Include links to PRs and issues. Changelog is a release artifact — committed to the repository.                                                     |       | 2026-03-16 |
| DEC-396 | MEDIUM   | Phase 2 (Release Process)      | Releases are created by the CI/CD pipeline — not manually. Create a GitHub Release with auto-generated notes for every version tag. Deployment to production is triggered by release creation (or promotion from staging). Hotfix releases follow the same pipeline with an expedited review process.                                                         |       | 2026-03-16 |
| DEC-397 | MEDIUM   | Phase 2 (Monorepo Strategy)    | Use workspace-aware tooling (npm workspaces, Turborepo, Nx). Each package has its own `package.json`, tests, and build. CI runs only affected packages on PRs (incremental builds). Shared dependencies are hoisted to the root. Version packages independently unless there's a reason for lock-step versioning.                                             |       | 2026-03-16 |
| DEC-398 | LOW      | Phase 2 (Git Hygiene)          | Delete merged branches within 24 hours (automate via CI). Prune stale branches monthly. Keep `.gitignore` comprehensive and up to date. Use `.gitattributes` for line ending normalization (`* text=auto`). LFS for binary assets > 1MB. Limit repository size — no build artifacts, no large media files committed.                                          |       | 2026-03-16 |
