# Decisions: Database & Persistence

> Stack: database | Status: ACTIVE | Applicable: YES
>
> Created 2026-03-16. Best-practice decisions for database engine selection,
> schema management, query patterns, connection management, and data integrity
> for full-stack applications.

---

## Decided Items

| ID      | Priority | Scope                                | Decision                                                  | Notes                                                                                                                                                                                                                                                                                    | Date       |
| ------- | -------- | ------------------------------------ | --------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------- |
| DEC-321 | HIGH     | Phase 2 (Engine Selection)           | How should database engines be selected for new features? | Select the engine that fits the data model: relational (PostgreSQL) for transactional/relational data, document (MongoDB/Cosmos DB) for flexible schemas, key-value (Redis) for caching/sessions. Justify deviations in an ADR. Avoid polyglot persistence without clear need.           | 2026-03-16 |
| DEC-322 | HIGH     | Phase 2 (Schema Migrations)          | How must database schema changes be managed?              | All schema changes must use versioned, forward-only migration files tracked in source control. Migrations must be idempotent and rollback-safe. Use a migration tool (Prisma Migrate, Flyway, Liquibase, or knex migrations). Never apply manual DDL to shared environments.             | 2026-03-16 |
| DEC-323 | HIGH     | Phase 2 (Connection Pooling)         | What connection management strategy is required?          | Use connection pooling for all database connections. Configure pool size based on workload (min 2, max based on DB max_connections / app instances). Set connection timeout and idle timeout. Use health checks to evict stale connections. Never open unbounded connections.            | 2026-03-16 |
| DEC-324 | HIGH     | Phase 2 (Query Safety)               | What query safety rules are mandatory?                    | Use parameterized queries or ORM-generated queries exclusively. Raw SQL string concatenation is prohibited. Enable slow query logging (threshold: 500ms). All queries accessing user-facing data must be covered by an index. N+1 query patterns must be detected and resolved.          | 2026-03-16 |
| DEC-325 | HIGH     | Phase 2 (Backup & Recovery)          | What backup and recovery requirements apply?              | Automated daily backups with point-in-time recovery (PITR) enabled. Backup retention minimum 30 days for production. Test restore procedure at least quarterly. Document RTO (Recovery Time Objective) and RPO (Recovery Point Objective) per database.                                  | 2026-03-16 |
| DEC-326 | MEDIUM   | Phase 2 (ORM / Query Builder)        | What data access layer pattern is recommended?            | Use an ORM or query builder (Prisma, Drizzle, TypeORM, or Knex) for standard CRUD operations. Raw queries are acceptable for complex reporting or performance-critical paths. Abstract data access behind a repository/service layer. Never expose ORM models directly in API responses. | 2026-03-16 |
| DEC-327 | MEDIUM   | Phase 2 (Indexing Strategy)          | What indexing governance is required?                     | Index all foreign keys and columns used in WHERE, ORDER BY, and JOIN clauses. Review query plans for queries above the slow-query threshold. Create composite indexes for multi-column queries. Drop unused indexes periodically. Document index rationale in migration files.           | 2026-03-16 |
| DEC-328 | MEDIUM   | Phase 2 (Naming Conventions)         | What database naming conventions are mandatory?           | Use snake*case for table and column names. Use plural nouns for table names (`users`, `orders`). Prefix boolean columns with `is*`or`has*`. Use `\_id`suffix for foreign key columns. Name indexes descriptively:`idx*{table}\_{columns}`.                                               | 2026-03-16 |
| DEC-329 | MEDIUM   | Phase 2 (Soft Deletes & Audit)       | What data deletion and audit trail strategy is required?  | Use soft deletes (`deleted_at` timestamp) for business-critical entities. Hard delete only for ephemeral or PII-regulated data after retention period. Maintain `created_at`, `updated_at` timestamps on all tables. Consider change-data-capture for audit trails on sensitive tables.  | 2026-03-16 |
| DEC-330 | MEDIUM   | Phase 2 (Environment Data Isolation) | How must database data be isolated across environments?   | Each environment (dev, staging, production) must use a separate database instance. Production data must never be copied to lower environments without anonymization/masking. Seed scripts provide consistent test data for dev/staging.                                                  | 2026-03-16 |
