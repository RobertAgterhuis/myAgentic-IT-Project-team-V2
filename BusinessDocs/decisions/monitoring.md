# Decisions: Monitoring & Incident Response

> Stack: monitoring | Status: ACTIVE | Applicable: YES
>
> Created 2026-03-16. Best-practice decisions for uptime monitoring, SLO/SLI
> management, incident response, on-call, and post-incident review for
> full-stack applications.

---

## Decided Items

| ID      | Priority | Scope                               | Decision                                                                                                                                                                                                                                                                                                                                                               | Notes | Date       |
| ------- | -------- | ----------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----- | ---------- |
| DEC-417 | HIGH     | Phase 2 (SLOs and SLIs)             | Define SLOs (Service Level Objectives) for every customer-facing service. Required SLIs: availability (% uptime), latency (p95), error rate (% 5xx). Set error budgets per SLO. When error budget is exhausted, prioritize reliability work over features. Review SLOs quarterly.                                                                                      |       | 2026-03-16 |
| DEC-418 | HIGH     | Phase 2 (Uptime Monitoring)         | Monitor all production endpoints with external synthetic checks at 1-minute intervals minimum. Check from multiple geographic regions. Monitor health endpoints (liveness, readiness). Alert on downtime within 2 minutes. Track uptime as a percentage per calendar month.                                                                                            |       | 2026-03-16 |
| DEC-419 | HIGH     | Phase 2 (Incident Response Process) | Define incident severity levels: SEV1 (service down, all users affected), SEV2 (major degradation), SEV3 (minor impact), SEV4 (cosmetic/non-urgent). Each severity has defined response times: SEV1 < 15min, SEV2 < 1hr, SEV3 < 4hr, SEV4 < 1 business day. Assign incident commander for SEV1/SEV2. Communicate status externally for SEV1/SEV2.                      |       | 2026-03-16 |
| DEC-420 | HIGH     | Phase 2 (Alerting Strategy)         | Alerts must be actionable — every alert must have a runbook link. Use symptom-based alerting (error rate, latency) over cause-based (CPU, memory) where possible. Route alerts by severity: SEV1/SEV2 → PagerDuty/Teams call, SEV3 → Slack/Teams channel, SEV4 → ticketing system. Review alert noise quarterly — prune or tune alerts with > 50% false-positive rate. |       | 2026-03-16 |
| DEC-421 | HIGH     | Phase 2 (On-Call)                   | Maintain an on-call rotation for all production services (at minimum, the owning team). On-call engineers must acknowledge SEV1/SEV2 alerts within 15 minutes. Provide on-call handoff documentation at rotation change. Compensate on-call fairly. On-call engineers must have production access (JIT if necessary).                                                  |       | 2026-03-16 |
| DEC-422 | MEDIUM   | Phase 2 (Post-Incident Review)      | Conduct blameless post-incident review (postmortem) within 3 business days for all SEV1/SEV2 incidents. Document: timeline, root cause, impact, detection method, resolution, action items with owners and due dates. Share postmortem with the engineering organization. Track action item completion.                                                                |       | 2026-03-16 |
| DEC-423 | MEDIUM   | Phase 2 (Runbooks)                  | Every production service and every alert must have a linked runbook. Runbooks must include: symptom description, diagnostic steps, remediation steps, escalation path, and rollback procedure. Store runbooks in the repository alongside the service code. Review and test runbooks quarterly.                                                                        |       | 2026-03-16 |
| DEC-424 | MEDIUM   | Phase 2 (Status Page)               | Any product with external users must have a public status page (Statuspage, Instatus, or equivalent). Update status page within 5 minutes of confirmed SEV1 incident. Show component-level status (API, Web App, Authentication, etc.). Post incident updates at least every 30 minutes during active incidents. Publish postmortem summary on resolution.             |       | 2026-03-16 |
| DEC-425 | MEDIUM   | Phase 2 (Real User Monitoring)      | Collect Core Web Vitals (LCP, INP, CLS) from real users in production. Segment RUM data by: page/route, device type, connection speed, and geography. Alert on sustained degradation of p75 metrics. Use RUM data — not just synthetic tests — for performance optimization decisions.                                                                                 |       | 2026-03-16 |
| DEC-426 | LOW      | Phase 2 (Synthetic Monitoring)      | Implement synthetic user journey tests for critical flows (login, checkout, onboarding) running every 5–15 minutes. Synthetic tests execute against production (read-only, with test accounts). Alert on synthetic failure. Use synthetic monitoring data to validate SLOs.                                                                                            |       | 2026-03-16 |
