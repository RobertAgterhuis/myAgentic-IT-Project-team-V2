# Decisions: Error Handling & Resilience

> Stack: error-handling | Status: ACTIVE | Applicable: YES
>
> Created 2026-03-16. Best-practice decisions for global error strategies, retry
> policies, circuit breakers, and fault tolerance for full-stack applications.

---

## Decided Items

| ID      | Priority | Scope                                | Decision                                                                                                                                                                                                                                                                                                                                          | Notes | Date       |
| ------- | -------- | ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----- | ---------- |
| DEC-359 | HIGH     | Phase 2 (Global Error Strategy)      | Every service must have a global error handler that catches unhandled exceptions, logs them with full context (stack trace, request ID, user context), returns a safe error response (no internal details), and prevents process crashes. Use middleware/interceptor patterns — never try/catch in every function.                                |       | 2026-03-16 |
| DEC-360 | HIGH     | Phase 2 (Error Classification)       | Classify errors into: (1) Client errors (4xx — validation, auth, not found — do NOT retry), (2) Server errors (5xx — internal failure — log, alert, may retry), (3) Transient errors (timeouts, rate limits — retry with backoff), (4) Fatal errors (OOM, config missing — crash and restart). Each class has distinct handling behavior.         |       | 2026-03-16 |
| DEC-361 | HIGH     | Phase 2 (Retry Policy)               | Use exponential backoff with jitter for all retries. Maximum 3 retry attempts by default. Never retry non-idempotent operations without explicit idempotency guarantees. Configuration: `initialDelay: 200ms`, `maxDelay: 30s`, `jitterFactor: 0.5`. Log every retry attempt with attempt number.                                                 |       | 2026-03-16 |
| DEC-362 | HIGH     | Phase 2 (Circuit Breaker)            | Apply circuit breakers to all external service calls (APIs, databases, third-party services). Configurations: failure threshold (5 failures in 30s → open), recovery timeout (30s → half-open), success threshold (3 successes → close). Expose circuit breaker state in health checks. Use a proven library (opossum, Polly, resilience4j).      |       | 2026-03-16 |
| DEC-363 | MEDIUM   | Phase 2 (Timeout Strategy)           | Set explicit timeouts on all outbound calls: HTTP requests (default 10s), database queries (default 30s), message queue operations (default 5s). Never use infinite timeouts. Client-facing request timeout < sum of downstream timeouts. Document timeout values in service configuration.                                                       |       | 2026-03-16 |
| DEC-364 | MEDIUM   | Phase 2 (Graceful Degradation)       | When a non-critical dependency fails, the service must continue operating with degraded functionality — not return a 500. Implement fallbacks: cached data, default values, feature toggles. Communicate degraded state via response headers or metadata. Log degradation events at WARN level.                                                   |       | 2026-03-16 |
| DEC-365 | MEDIUM   | Phase 3 (Client-Side Error Handling) | Implement React error boundaries at route and feature level. Show user-friendly error messages — never raw error strings or stack traces. Provide retry/reload actions for recoverable errors. Log client errors to the server with context (browser, URL, user action). Distinguish between network errors, auth errors, and application errors. |       | 2026-03-16 |
| DEC-366 | MEDIUM   | Phase 2 (Async Error Handling)       | Message queue consumers must implement dead-letter queues (DLQ) for failed messages after max retries. Background jobs must log failures and support manual retry. Event handlers must not throw unhandled exceptions. All async error paths must be monitored and alerted on. Never silently swallow errors.                                     |       | 2026-03-16 |
