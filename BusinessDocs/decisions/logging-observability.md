# Decisions: Logging & Observability

> Stack: logging-observability | Status: ACTIVE | Applicable: YES
>
> Created 2026-03-16. Best-practice decisions for structured logging, distributed
> tracing, metrics collection, alerting, and observability governance for
> full-stack applications.

---

## Decided Items

| ID      | Priority | Scope                         | Decision                                       | Notes                                                                                                                                                                                                                                                                                                     | Date       |
| ------- | -------- | ----------------------------- | ---------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------- |
| DEC-349 | HIGH     | Phase 2 (Structured Logging)  | What logging format is mandatory?              | All application logs must use structured JSON format. Every log entry must include: `timestamp` (ISO 8601), `level`, `message`, `service`, `traceId`, `spanId`. Use a logging library (pino, winston, or serilog) — never `console.log` in production code.                                               | 2026-03-16 |
| DEC-350 | HIGH     | Phase 2 (Log Levels)          | What log level policy is mandatory?            | Use standard log levels: `FATAL` (system unusable), `ERROR` (operation failed), `WARN` (degraded but functional), `INFO` (business events), `DEBUG` (developer diagnostics). Default production level: `INFO`. Never log at `DEBUG` in production without dynamic toggle.                                 | 2026-03-16 |
| DEC-351 | HIGH     | Phase 2 (Distributed Tracing) | What distributed tracing standard is required? | Implement OpenTelemetry (OTLP) for distributed tracing. Propagate W3C `traceparent` and `tracestate` headers across all service boundaries. Every inbound HTTP request must generate or propagate a trace. Trace context must appear in all log entries for correlation.                                  | 2026-03-16 |
| DEC-352 | HIGH     | Phase 2 (PII in Logs)         | What rules govern sensitive data in logs?      | Never log passwords, tokens, API keys, credit card numbers, or full PII (SSN, passport). Log only anonymized/masked identifiers (e.g., last 4 digits, hashed user IDs). Apply allowlist-based log field filtering. Review log output in security audits.                                                  | 2026-03-16 |
| DEC-353 | HIGH     | Phase 2 (Log Aggregation)     | Where must logs be aggregated?                 | Centralize all application, infrastructure, and audit logs in a single log aggregation platform (ELK, Azure Monitor, Datadog, or Grafana Loki). Logs must be searchable within 2 minutes of emission. Retain production logs minimum 90 days, audit logs minimum 1 year.                                  | 2026-03-16 |
| DEC-354 | MEDIUM   | Phase 2 (Application Metrics) | What application metrics must be collected?    | Collect the four golden signals: latency, traffic (throughput), errors (rate), and saturation (resource usage). Expose metrics in Prometheus/OpenTelemetry format. Include business metrics (orders/sec, logins/sec) alongside technical metrics. Use histograms for latency, counters for errors.        | 2026-03-16 |
| DEC-355 | MEDIUM   | Phase 2 (Health Endpoints)    | What health check endpoints are mandatory?     | Every service must expose: `/health/live` (liveness — process is running), `/health/ready` (readiness — dependencies reachable), `/health/startup` (one-time initialization complete). Return HTTP 200 with JSON body including component statuses. Orchestrators (K8s) use these for automated recovery. | 2026-03-16 |
| DEC-356 | MEDIUM   | Phase 2 (Alerting Rules)      | What alerting strategy is mandatory?           | Define alerts based on symptoms, not causes (e.g., "error rate > 5%" not "CPU > 80%"). Use severity tiers: P1 (page immediately), P2 (page during business hours), P3 (ticket). Every alert must have a linked runbook. Review and prune alert rules quarterly to prevent alert fatigue.                  | 2026-03-16 |
| DEC-357 | MEDIUM   | Phase 2 (Dashboards)          | What observability dashboards are required?    | Maintain per-service dashboards showing: request rate, error rate, latency (p50/p95/p99), saturation. Maintain a system-level overview dashboard. All dashboards must be version-controlled (dashboard-as-code). Use consistent naming and layout conventions across dashboards.                          | 2026-03-16 |
| DEC-358 | LOW      | Phase 2 (Audit Logging)       | What events require audit logging?             | Audit log: authentication events (login, logout, MFA, failed attempts), authorization decisions (granted, denied), data access to sensitive resources, admin operations, configuration changes. Audit logs are immutable — append-only with tamper detection. Stored separately from application logs.    | 2026-03-16 |
