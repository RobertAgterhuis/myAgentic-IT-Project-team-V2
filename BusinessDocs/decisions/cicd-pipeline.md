# Decisions: CI/CD Pipeline Design

> Stack: cicd-pipeline | Status: ACTIVE | Applicable: YES
>
> Created 2026-03-16. Best-practice decisions for pipeline architecture, artifact
> management, deployment strategies, rollback procedures, and pipeline security
> for full-stack applications. Complements github-actions.md (which covers the
> GitHub Actions tool) with platform-agnostic pipeline design patterns.

---

## Decided Items

| ID      | Priority | Scope                                 | Decision                                              | Notes                                                                                                                                                                                                                                                                                                                                                                                                                                                                  | Date       |
| ------- | -------- | ------------------------------------- | ----------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------- |
| DEC-499 | HIGH     | Phase 2 (Pipeline Architecture)       | What CI/CD pipeline architecture is mandatory?        | Separate CI (build + test + scan) from CD (deploy). CI runs on every PR and push to main. CD runs on merge to main (auto-deploy to staging) and on release tag (promote to production). Pipeline configuration lives in the repository (pipeline-as-code). No manual steps in the deployment pipeline — fully automated from commit to production.                                                                                                                     | 2026-03-16 |
| DEC-500 | HIGH     | Phase 2 (Build Reproducibility)       | What build reproducibility guarantees are mandatory?  | Builds must be reproducible: same commit produces the same artifact. Pin all dependencies via lockfiles (package-lock.json, requirements.txt). Use exact-version base images for Docker builds. Include build metadata in artifacts (commit SHA, build number, timestamp). Cache build dependencies for speed but validate cache integrity. Build once, deploy everywhere — same artifact across all environments.                                                     | 2026-03-16 |
| DEC-501 | HIGH     | Phase 2 (Pipeline Security)           | What security checks must the CI/CD pipeline enforce? | Mandatory pipeline security gates: dependency vulnerability scan (fail on HIGH/CRITICAL), SAST (static analysis), secret scanning (fail on detection), license compliance check, container image scanning (if Docker). Pipeline credentials must be stored in the CI/CD platform's secret manager — never in pipeline config files. Use OIDC for cloud provider authentication — no long-lived credentials.                                                            | 2026-03-16 |
| DEC-502 | HIGH     | Phase 2 (Artifact Management)         | What artifact management strategy is mandatory?       | Publish build artifacts to a registry: container images to a container registry (ACR, ECR, GHCR), npm packages to a private registry if applicable. Tag artifacts with the Git commit SHA and semantic version. Retain artifacts for at least 90 days. Never deploy artifacts from a developer's machine — only from CI/CD. Sign container images and verify signatures before deployment.                                                                             | 2026-03-16 |
| DEC-503 | HIGH     | Phase 2 (Deployment Strategy)         | What deployment strategies must be supported?         | Support at minimum: rolling deployment (zero-downtime default), and blue-green or canary for critical services. Choose strategy based on risk and rollback speed requirements. Canary: route 5–10% traffic first, promote after success criteria met (error rate, latency). All strategies must support automated rollback on failure. Database migrations must be deployment-strategy-aware (backward compatible, see DEC-322).                                       | 2026-03-16 |
| DEC-504 | HIGH     | Phase 2 (Rollback Procedure)          | What rollback requirements are mandatory?             | Every deployment must be rollback-capable within 5 minutes. Rollback redeploys the previous known-good artifact — not a rebuild. Database migrations must be backward compatible to support rollback (no destructive migrations during deployment). Automate rollback trigger: if error rate > 5% or health checks fail within 10 minutes post-deploy. Document manual rollback procedure for edge cases. Test rollback in staging before first production deployment. | 2026-03-16 |
| DEC-505 | MEDIUM   | Phase 2 (Pipeline Performance)        | What pipeline performance targets are mandatory?      | CI pipeline (build + test + scan) must complete within 15 minutes for PRs. Full deployment pipeline (CI + staging deploy + E2E + production promote) within 30 minutes. Use parallelism: run lint, unit tests, and security scans concurrently. Cache aggressively: dependencies, Docker layers, build outputs. Monitor pipeline duration — alert on sustained > 20% degradation.                                                                                      | 2026-03-16 |
| DEC-506 | MEDIUM   | Phase 2 (Pipeline as Code)            | What pipeline-as-code standards are mandatory?        | Pipeline definitions live in the repository (`.github/workflows/`, `azure-pipelines.yml`, or equivalent). Pipeline changes go through the same PR review process as application code. Use reusable workflows/templates for common patterns (build, test, deploy). Pin action/plugin versions to SHAs (not tags). Document pipeline architecture with a visual diagram.                                                                                                 | 2026-03-16 |
| DEC-507 | MEDIUM   | Phase 2 (Environment Promotion Gates) | What promotion gates must exist between environments? | Staging → Production requires: all tests passing (unit, integration, E2E, contract), security scans clean (no new HIGH/CRITICAL), performance benchmark within tolerance (DEC-459), and manual approval for first-time deployments of new services. Automated approval for subsequent deployments that pass all gates. Feature flag verification: no unreleased flags enabled in production.                                                                           | 2026-03-16 |
| DEC-508 | LOW      | Phase 2 (Pipeline Observability)      | What CI/CD pipeline observability is required?        | Track pipeline metrics: success/failure rate, duration (p50/p95), flaky test rate, queue wait time. Dashboard showing pipeline health across all repositories. Alert on sustained failure rate > 10%. Track deployment frequency, lead time, change failure rate, and mean time to recovery (DORA metrics). Share DORA metrics with the engineering team monthly.                                                                                                      | 2026-03-16 |
