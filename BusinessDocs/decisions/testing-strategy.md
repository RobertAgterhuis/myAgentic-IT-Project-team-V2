# Decisions: Testing Strategy

> Stack: testing-strategy | Status: ACTIVE | Applicable: YES
>
> Created 2026-03-16. Unified testing pyramid, test governance, contract
> testing, load testing, and test data management for full-stack applications.
> Consolidates and extends scattered testing decisions in react.md, cross-cutting.md,
> and playwright.md into a single authoritative source.

## Decided Items

| ID      | Priority | Scope                                | Decision                                                                                                                                                                                                                                                                                                                                                                                               | Notes | Date       |
| ------- | -------- | ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----- | ---------- |
| DEC-453 | HIGH     | Phase 2 (Testing Pyramid)            | Follow the testing pyramid: many unit tests (fast, isolated), fewer integration tests (component boundaries), fewer E2E tests (critical user journeys only). Target ratio: ~70% unit, ~20% integration, ~10% E2E. Every test level has a clear purpose — no redundant coverage across levels.                                                                                                          |       | 2026-03-16 |
| DEC-454 | HIGH     | Phase 2 (Unit Testing Standards)     | Use Vitest as the single test runner (see DEC-310). Test behavior, not implementation details. Each unit test must be independent, deterministic, and fast (< 100ms). Mock external dependencies — never hit real databases, APIs, or file systems. Name tests descriptively: `should [behavior] when [condition]`.                                                                                    |       | 2026-03-16 |
| DEC-455 | HIGH     | Phase 2 (Integration Testing)        | Integration tests verify component interactions: API routes against real middleware stacks, database queries against test databases, service-to-service contracts. Use test containers (Testcontainers or Docker Compose) for database/cache dependencies. Integration tests run in CI on every PR — not just nightly.                                                                                 |       | 2026-03-16 |
| DEC-456 | HIGH     | Phase 2 (E2E Testing)                | Use Playwright for E2E tests. Test critical user journeys only (login, core CRUD flows, checkout, onboarding). E2E tests run against a fully deployed environment (staging or preview). Maximum 30-minute E2E suite runtime — prioritize ruthlessly. Flaky tests are treated as P2 bugs — fix or delete within 5 business days.                                                                        |       | 2026-03-16 |
| DEC-457 | HIGH     | Phase 2 (Contract Testing)           | Use consumer-driven contract tests (Pact, or OpenAPI-based contract testing) for all API boundaries. Contract tests verify that provider API changes don't break consumers. Run contract tests in CI before deployment. Breaking contract test = blocked deployment. Contract tests replace the need for many integration tests across service boundaries.                                             |       | 2026-03-16 |
| DEC-458 | HIGH     | Phase 2 (Coverage Requirements)      | Minimum coverage thresholds: 80% line coverage for business logic, 70% for API routes, 60% for UI components. Coverage is measured per PR — new code must meet thresholds. Coverage-only metrics are insufficient — review test quality in code review. Never chase 100% — diminishing returns beyond 85%. Critical paths (auth, payments) require explicit test plans regardless of coverage numbers. |       | 2026-03-16 |
| DEC-459 | MEDIUM   | Phase 2 (Load & Performance Testing) | Run load tests against critical API endpoints before major releases. Define performance baselines: response time (p95), throughput (req/s), error rate under load. Use k6, Artillery, or Gatling. Test scenarios: normal load, peak load (2x normal), and spike (sudden 10x burst). Performance regression (> 20% degradation from baseline) blocks release.                                           |       | 2026-03-16 |
| DEC-460 | MEDIUM   | Phase 2 (Test Data Management)       | Use factories/builders (not fixtures) for test data creation. Test data must be isolated per test — no shared mutable state. Seed scripts provide consistent baseline data for integration/E2E environments. Production data must never be used in tests without anonymization. Provide a test data reset mechanism for E2E environments.                                                              |       | 2026-03-16 |
| DEC-461 | MEDIUM   | Phase 2 (Visual Regression Testing)  | Use visual regression tools (Chromatic, Percy, or Playwright visual comparisons) for UI components. Baseline screenshots are maintained in CI. Visual changes require explicit approval. Run visual tests on Storybook stories and critical page layouts. Visual regression tests supplement — not replace — functional tests.                                                                         |       | 2026-03-16 |
| DEC-462 | MEDIUM   | Phase 2 (Test Environment Strategy)  | Unit tests: in-memory, no external dependencies. Integration tests: local Docker containers or test databases. E2E tests: dedicated staging environment or ephemeral preview environments. Tests must not depend on external services being available — use stubs/mocks for third-party APIs. Each PR gets an isolated test execution — no cross-PR interference.                                      |       | 2026-03-16 |
