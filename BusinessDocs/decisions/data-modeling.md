# Decisions: Data Modeling & Contracts

> Stack: data-modeling | Status: ACTIVE | Applicable: YES
>
> Created 2026-03-16. Best-practice decisions for data schema design, validation
> libraries, API contracts, serialization, and data governance for full-stack
> applications.

## Decided Items

| ID      | Priority | Scope                                  | Decision                                                                                                                                                                                                                                                                                                                                                | Notes | Date       |
| ------- | -------- | -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----- | ---------- |
| DEC-427 | HIGH     | Phase 2 (Schema Validation Library)    | Use a single validation library across backend and frontend for type consistency: Zod (TypeScript-first, excellent type inference), Yup, or Joi. The chosen library must support: type coercion, custom validators, friendly error messages, and TypeScript type generation. Validate at all system boundaries.                                         |       | 2026-03-16 |
| DEC-428 | HIGH     | Phase 2 (API Contract Strategy)        | Use contract-first (OpenAPI spec → code) or code-first with generated spec (code → auto-OpenAPI). API contracts must be versioned in source control. Run contract tests in CI: verify that the API implementation matches the declared spec. Contract breaking changes require a version bump and migration guide.                                      |       | 2026-03-16 |
| DEC-429 | HIGH     | Phase 2 (Data Transfer Objects)        | Use explicit DTOs (Data Transfer Objects) for API request/response shapes — never expose internal domain models or database entities directly. Map between DTOs and domain models explicitly. DTOs must be validated (DEC-427) and documented (OpenAPI schema). Frontend and backend must share type definitions or validate against the same schema.   |       | 2026-03-16 |
| DEC-430 | HIGH     | Phase 2 (Required vs. Optional Fields) | All fields must be explicitly typed as required or optional. Use `null` to represent intentional absence — not `undefined` (undefined means "field not present" in JSON). Default values must be documented in the schema. Avoid `any` types — every field has a specific type. Use discriminated unions for polymorphic data.                          |       | 2026-03-16 |
| DEC-431 | MEDIUM   | Phase 2 (Serialization)                | Use JSON as the default serialization format. Dates must be serialized as ISO 8601 strings (UTC). Numbers must be serialized as JSON numbers (not strings) unless precision requires string encoding (e.g., financial values). Enums are serialized as strings, not integers. Undefined fields are omitted from JSON — explicit null is preserved.      |       | 2026-03-16 |
| DEC-432 | MEDIUM   | Phase 2 (Domain Model Design)          | Separate domain models (business logic) from persistence models (database schema) and presentation models (DTOs). Use value objects for well-defined concepts (Email, Money, DateRange). Enforce invariants in domain model constructors/factories. Prefer composition over inheritance for model relationships.                                        |       | 2026-03-16 |
| DEC-433 | MEDIUM   | Phase 2 (Schema Evolution)             | New fields default to optional — never add a new required field to an existing schema. Removing or renaming fields is a breaking change. Use the expand-and-contract pattern: add new field → migrate consumers → remove old field. Schema changes must be backward-compatible for at least one version. Document migration paths for breaking changes. |       | 2026-03-16 |
| DEC-434 | LOW      | Phase 2 (Shared Types Package)         | Publish shared TypeScript types in a common package (monorepo workspace package or npm package). Auto-generate types from OpenAPI spec or database schema. Never duplicate type definitions manually across frontend and backend. Shared package version must be pinned in consuming packages.                                                          |       | 2026-03-16 |
